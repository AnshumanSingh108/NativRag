# Nativ RAG

A multilingual (English, Hindi) question-answering chatbot for
region-specific questions about Bangladesh, India and Qatar. It is a
retrieval-augmented generation (RAG) system: answers are generated by a
local Ollama LLM (`llama3.2`, optionally LoRA fine-tuned) from documents
retrieved out of a ChromaDB knowledge base.

The data is the MultiNativQA dataset (ACL Findings 2025,
`docs/2025.findings-acl.770.pdf`). We do not replicate the paper's
zero-shot setup. We use its metrics (BERTScore F1, BLEU, ROUGE-1) to
measure our own RAG approach on the full test set.

## Vision and plan

**Goal.** A multilingual question-answering chatbot for questions about
Bangladesh, India and Qatar that answers in the user's language (English and
Hindi in the current data), grounded in retrieved native QA documents. The
benchmark paper is the source of the data and metrics, not a recipe to copy.

**Our approach.**
1. Index the training split as a retrieval knowledge base (`qa_kb/`).
2. Fine-tune Llama-3.2-3B with LoRA on prompts that already contain retrieved
   context, so the model learns to answer from documents (train + dev only;
   the test set stays held out).
3. Serve the model locally through Ollama and answer with retrieval at
   question time.
4. Evaluate on the entire test set of all three countries with BERTScore,
   BLEU and ROUGE-1, reported per country and overall, and split by whether
   the reference answer was retrieved.

**Plan.**
- Done: steps 1-3, the evaluation pipeline and the results-table script.
- Next: run the full evaluation (6,180 questions) on a GPU machine, produce
  the final results table, and fill it into this README.
- Open options, not decided: a base-`llama3.2` baseline on the same RAG setup
  to show what fine-tuning adds; the Country PDF knowledge base as an extra
  source; the paper's LLM-as-judge and human evaluation; Bangla coverage
  (the current test sets contain only English and Hindi).

## How it works

```
question -> embed (multilingual mpnet) -> top-k retrieval from qa_kb/ (ChromaDB)
         -> prompt = system prompt + numbered documents + question
         -> Ollama LLM -> answer
```

- **Knowledge base (`qa_kb/`)**: built from the **train** split only, so the
  test set is never retrievable.
- **Test sets** (`data/<country>/test.json`): Bangladesh 1,113 (English),
  India 2,745 (Hindi), Qatar 2,322 (English). 6,180 questions in total.
- **Fine-tuning**: LoRA on Llama-3.2-3B-Instruct using **train + dev**. The
  test set is never used for training. Training prompts contain retrieved
  context in the same format used at answer time, and a training question's
  own KB record is excluded from its context.

## Setup

```bash
pip install -r requirements.txt
```

Install [Ollama](https://ollama.com/download) and pull the base model:
`ollama pull llama3.2` (used for the baseline and as the default for
`main.py --kb qa`). Data lives in `data/<country>/{train,dev,test}.json`.
To use the fine-tuned chatbot you also need `nativrag-finetuned` registered
(section 3).

## 1. Build the QA knowledge base (`qa_kb/`)

Indexes the **train** split of the three countries.

```bash
python -m scripts.build_qa_kb
```

`qa_documents/` is already included. To regenerate it from `data/`, run
`python -m scripts.prepare_qa_data` first.

## 2. Fine-tune llama3.2 (CUDA GPU required)

Use a machine with a CUDA GPU (~16 GB). Accept Meta's license for
`meta-llama/Llama-3.2-3B-Instruct` on Hugging Face and run
`huggingface-cli login` (or use an ungated copy such as
`unsloth/Llama-3.2-3B-Instruct`, which is what the current adapter used).

```bash
pip install -r requirements.txt -r requirements-train.txt

# a) Build training data: train + dev, with context retrieved from qa_kb
#    -> finetune_data/training_data.jsonl (git-ignored)
python -m scripts.build_finetune_data

# b) Train the LoRA adapter -> lora_adapter/
python -m scripts.train_lora            # add --resume to continue a run
```

What step (a) does: for every train and dev question it retrieves the top 5
documents from `qa_kb/`, drops the question's own KB record so the reference
answer is not in its prompt, builds the system and user messages with the same
`build_messages` the chatbot uses, and appends the reference answer as the
assistant turn. The test split is never read. Step (b) renders each example in
Llama-3 chat format and computes the loss on the answer tokens only.

Hyperparameters follow the paper: Adam, lr 2e-4, LoRA r=64, alpha=16,
effective batch size 16, 1 epoch. Max sequence length is 3072 because our
prompts carry retrieved documents. If you hit out-of-memory errors, lower
`--max-seq-len`. The trained adapter is saved in `lora_adapter/`, so the GPU
machine is no longer needed once you have copied it.

## 3. Register the fine-tuned model in Ollama

Ollama does not train models. It must serve a model called
`nativrag-finetuned` (the name set in `config.py`).

**Known issue: the `ADAPTER` route does not work on current Ollama.** A
Modelfile with `FROM llama3.2` and an `ADAPTER` line pointing at `lora_adapter/`
(what an earlier version of this repo generated) is rejected by Ollama 0.40.18
with `Error: LoRA adapters are no longer supported`. The repo no longer has
a script for that route. On the same
version, importing a safetensors folder (`FROM <folder>`), with or without
`-q`, fails with `MLX runtime is not available` on Windows. The only route
that worked is a GGUF file. The adapter itself is fine: `lora_adapter/` is
valid and nothing needs to be retrained.

The route that worked (CPU only, no GPU needed; about 6.4 GB of base weights
plus about 10 GB of intermediates, all deletable once the model is registered):

**a) Merge the adapter into the base model.** The base is
`unsloth/Llama-3.2-3B-Instruct`, the one named in
`lora_adapter/adapter_config.json` (not gated). The script downloads it,
applies `W' = W + (alpha / r) * B @ A` to each of the 196 adapted weights one
tensor at a time (so it fits in ~5 GB of free RAM), and fails if the adapter
and base do not match. It needs only `torch`, `safetensors` and
`huggingface_hub`, which `requirements.txt` already installs (via
`transformers`).

```bash
python -m scripts.merge_adapter --output-dir <dir>/merged
```

If the download stalls, stop it and rerun. Setting `HF_HUB_DISABLE_XET=1`
(plain HTTPS) was more reliable here. A rerun may restart the big shard
rather than resume it.

**b) Convert the merged model to GGUF (Q8_0, about 3.4 GB)** with llama.cpp's
official converter. It is not part of this repo: clone it into a scratch
folder and read it before running.

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/ggml-org/llama.cpp <dir>/llamacpp
cd <dir>/llamacpp && git sparse-checkout set gguf-py conversion models/templates
pip install --target <dir>/ggufpkg gguf sentencepiece    # keeps your venv untouched
PYTHONPATH=<dir>/ggufpkg python <dir>/llamacpp/convert_hf_to_gguf.py <dir>/merged \
    --outtype q8_0 --outfile <dir>/nativrag-q8_0.gguf
```

`sentencepiece` must be installed even though Llama 3 does not use it: the
converter tries it first and crashes with `ModuleNotFoundError` instead of
falling back to the BPE tokenizer.

**c) Register the GGUF.** Put the GGUF at `models/nativrag-q8_0.gguf` (the
`models/` folder is git-ignored). The repo `Modelfile` (tracked) is
the working version: `FROM ./models/nativrag-q8_0.gguf`, a `TEMPLATE`, the
`SYSTEM` prompt and `PARAMETER` lines, with no `ADAPTER` line.

The `TEMPLATE` matters. The adapter was trained on plain Llama-3 headers
(`format_prompt` in `scripts/train_lora.py`: no "Cutting Knowledge Date" and
no date line), while Llama-3.2's stock template adds both. The `Modelfile`
`TEMPLATE` reproduces the training layout. Check it after registering: for a
system + user pair, Ollama's `prompt_eval_count` should equal the token count
of `format_prompt(messages)` (17, 26 and 33 on three test prompts, which is
what we got). Ollama prefers a template embedded in the GGUF when it can use
one, but it did not use the plain template we embedded (reason not
investigated), so the `Modelfile` block is what takes effect (`ollama show nativrag-finetuned` reports
`template source: go_template`). Register it:

```bash
ollama create nativrag-finetuned -f Modelfile
ollama list        # nativrag-finetuned (about 3.4 GB) must appear
```

The registered model is the fine-tuned weights stored in Q8_0, not the exact
bf16 weights that were trained, and it is a different quantization from the
Q4 `llama3.2` baseline. Mention this when reporting results. Once registered,
`<dir>/merged`, the GGUF, the llama.cpp clone and the Hugging Face cache
(`~/.cache/huggingface`) can be deleted; keep the GGUF if you want to
re-register or move the model to another machine.

## 4. Evaluate on the full test set

Ollama must be running and `nativrag-finetuned` registered. Always pass
`--llm-model` explicitly: without it the script falls back to the base model
when the fine-tuned one is missing, which would silently give you baseline
numbers.

```bash
# Quick check (5 samples per country). --output keeps it from sharing a
# filename with the full run (qa_nativrag-finetuned.json)
python -m scripts.evaluate --kb qa --sample-size 5 --llm-model nativrag-finetuned \
    --output evaluation_results/check_5.json

# Full test set, all 3 countries (6,180 questions; slow without a GPU)
python -m scripts.evaluate --kb qa --sample-size 0 --llm-model nativrag-finetuned
```

`--country india` limits a run to one country; `--top-k` changes how many
documents are retrieved (default 5). `--output <path>` overrides the output
file.

**Speed.** Measured with the Q8_0 model on a CPU-only Windows PC, generation
takes about 65-80 s per Hindi question and 15-20 s per English question. That
is roughly 65 hours for the full 6,180 questions (an estimate from the 15-question
check; scoring adds more), so run the full evaluation on a GPU machine, or
use `--sample-size N` (per country) for a subset.

**Pipeline check (5 per country, 15 questions).** This only confirms the
pipeline works; 15 samples are too few to judge quality.

| Country | Language | N | BERT-F1 | BLEU | ROUGE-1 |
|---|---|---|---|---|---|
| Bangladesh | English | 5 | 0.7136 | 0.0346 | 0.2826 |
| India | Hindi | 5 | 0.7553 | 0.2183 | 0.3386 |
| Qatar | English | 5 | 0.7328 | 0.0393 | 0.3078 |
| Overall | - | 15 | 0.7339 | 0.0974 | 0.3097 |

(Run with the training-format prompt template described in section 3. An
earlier run with the stock Llama-3.2 template scored BERT-F1 0.7283 / BLEU
0.0963 / ROUGE-1 0.2810 on the same questions. With 15 questions and
temperature 0.3 the difference is within noise, and only 2 of 15 answers were
identical between the runs, so it says nothing about which template is better.)

The full-test-set results table is still to be produced.

Metrics per question: BERTScore precision / recall / F1
(`bert-base-multilingual-cased`), ROUGE-1 F1 and sentence BLEU (0-1 scale,
Unicode-aware tokenization so Hindi is handled correctly).

Output: one JSON per run in `evaluation_results/`, named
`<kb>_<model>.json` (for example `qa_nativrag-finetuned.json`). It holds the
run config, a summary and every sample (query, reference, generated answer,
retrieved sources, all scores, and `answer_in_context`).

`answer_in_context` records whether the reference answer appears verbatim in
the retrieved documents. Scores are reported both overall and split by this
flag, because with a QA-pair KB part of the score can come from copying a
retrieved training answer rather than answering from knowledge.

## 5. Build the results tables

```bash
python -m scripts.make_results_table
# or: --input evaluation_results/<run>.json
```

Writes, next to the run JSON, `<run>_table.md`, `<run>_table.csv` and
`<run>_table.tex`:

- Main table: one row per country (Bangladesh/English, India/Hindi,
  Qatar/English) plus Overall, with N, BERT-P, BERT-R, BERT-F1, BLEU,
  ROUGE-1. Overall is the mean over all samples.
- Second table: overall scores split by `answer_in_context`.

Nothing in `evaluation_results/` is git-ignored: the `.gitignore` rule
`evaluation_results*.json` matches files named like that in the project root,
not files inside the folder. A run JSON holds every sample, about 35 KB per
15 questions, so a full run is on the order of 15 MB. Decide whether to
commit the JSONs or ignore them (for example `evaluation_results/*.json`) and
commit only the tables.

## Chat

```bash
python main.py --kb qa --llm-model nativrag-finetuned
```

Pass `--llm-model nativrag-finetuned` explicitly: with `--kb qa`, `main.py`
defaults to the base `llama3.2`, not the fine-tuned model. With
`--kb country_pdf` it picks `nativrag-finetuned` automatically if installed.
The Country PDF knowledge base is built with
`python -m scripts.build_country_kb` from `country_pdfs/`.

## Limitations

- Results are not comparable to the paper's tables: we use retrieval, a
  3B model, temperature 0.3, and per-country test sets rather than the
  paper's zero-shot Llama-3.1-8B setup.
- The paper's GPT-4o-as-judge and human evaluations are not implemented.
- The QA knowledge base can contain near-duplicates of test answers; check
  the `answer_in_context` split when interpreting scores.
- The registered model is Q8_0, not the exact trained bf16 weights. Its
  outputs were not compared against the unquantized merge.
- The 15-sample check is only a pipeline check. No full-test-set result
  exists yet.
- The chat template in `Modelfile` must stay in sync with
  `format_prompt` in `scripts/train_lora.py`. If it is removed, Ollama
  silently falls back to a ChatML template, which is wrong for Llama 3.
